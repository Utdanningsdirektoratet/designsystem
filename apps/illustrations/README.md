# Illustrations

Private Vite React app (`@udir-design/apps-illustrations`) that serves the illustration gallery.
Run it with `pnpm turbo run dev --filter=@udir-design/apps-illustrations` (port 4400, preview 4500).
In development there is no login: the app reads the files in `public/illustrations-assets/`, so run
`build:assets` once first.

## Hosting and login

The deployed app is a static site at `design.udir.no/illustrasjoner`. Udir staff sign in with Entra ID
(MSAL, single-page app registration, no secret). The artwork is not part of the site: it sits in a
private blob container, and the browser reads it with the user's own token (`storage.azure.com`
`user_impersonation`). Access is controlled by a role assignment for a staff group on that container.

A build has login when `VITE_AUTH_CLIENT_ID` is set. It also needs `VITE_AUTH_TENANT_ID`,
`VITE_STORAGE_ACCOUNT`, `VITE_STORAGE_CONTAINER` and `VITE_ASSET_VERSION`. Such builds use the base path
`/illustrasjoner/`. Register `https://design.udir.no/illustrasjoner/` and `http://localhost:4400/illustrasjoner/`
as redirect URIs.

- [.azure/designsystem-illustrations.bicep](../../.azure/designsystem-illustrations.bicep): storage account,
  private container, CORS and cleanup. Enable the account's static website once in the portal (Data
  management, Static website, index document `index.html`); the deploy identity can't change account settings.
- [.azure/designsystem-illustrations-frontdoor.bicep](../../.azure/designsystem-illustrations-frontdoor.bicep):
  adds only its own origin group, rule set and route to the shared Front Door.
- [.github/workflows/azure-illustrations-deploy.yml](../../.github/workflows/azure-illustrations-deploy.yml):
  fetches SVGs (cached), renders PNGs, uploads artwork to `<hash>-r<revision>/` and the app to
  `$web/illustrasjoner`. Set the repository variable `ILLUSTRATIONS_ASSET_REVISION` to force a full
  refetch when artwork changed in Figma without a `metadata.json` change.

## Where things live

| Path                           | In git | Purpose                                                                 |
| ------------------------------ | ------ | ----------------------------------------------------------------------- |
| `source/import-map.json`       | yes    | Reviewed mapping from Figma nodes to families, variants and properties. |
| `source/catalog/metadata.json` | yes    | Resolved catalog (IDs, names, properties, width, height and tags).      |
| `source/catalog/svg/`          | no     | SVGs downloaded from Figma by `fetch:svgs`.                             |
| `public/illustrations-assets/` | no     | SVGs, PNGs and metadata served by the app, generated by `build:assets`. |

The SVGs are not committed. They are downloaded from Figma when needed.

## Tasks

Run from this directory, or with `pnpm turbo run <task> --filter=@udir-design/apps-illustrations`.

- `fetch:svgs`: downloads the SVGs named in `metadata.json` that are missing from `source/catalog/svg`.
  Existing files are kept, so an interrupted run resumes. `--category=<id>` limits it to one category,
  and `--force` downloads everything again. It needs a Figma token only when something is missing.
- `build:assets`: runs `fetch:svgs`, then validates the SVGs and renders `png/<variant-id>.png` at
  exactly `round(width)` by `round(height)` into `public/illustrations-assets/`. It logs progress every
  100 PNGs. It takes no flags; set `ILLUSTRATIONS_CATEGORY=<id>` to limit both steps to one category.
- `dev` and `build` do not run `build:assets`, so the monorepo build needs no Figma token. `build` only
  produces the small app shell in `dist/`.
- `suggest:figma [--category=<id>]`: finds families and variants on the live Figma page that are missing
  from `import-map.json` and adds them. Without `--category` it checks every category. Existing entries
  are never changed, and it writes nothing if a new node is ambiguous (unknown property name or value,
  unmapped colour theme and similar). It also warns about entries whose Figma node is gone (for example
  a recreated component) and about nodes beyond the fetched depth. `--prune` removes the stale entries;
  follow it with `sync:figma --allow-removals`. Review the diff after.
- `sync:figma [--category=<id>]`: refreshes the category's entries in `metadata.json` from the live Figma
  page (bounds, tags, identity checks). `--allow-removals` is required to drop families or variants.
  Without `--category` it syncs every category in `sources`, one at a time, and stops at the first failure. Families keep
  their position in the file, so a sync with no real change gives no diff.
  It does not download artwork. Run `fetch:svgs --force --category=<id>` afterwards if artwork changed.
- `typecheck`, `lint`, `test:unit`: normal checks. Tests never access Figma.

The token is read from `FIGMA_TOKEN` in the environment or from the ignored workspace-root `.env.local`.
Never commit or log it.

## Figma sources

The `sources` map in `src/schema.ts` lists one Figma file and page per category, plus an `idPrefix`
that keeps generated IDs unique across files. A category without a source cannot be synced.

## Rules for the mapping

- IDs are lowercase kebab-case and never reassigned to another Figma node. Display names can change
  without renaming assets.
- Width and height come from the export frame bounds.
- Appearance properties are reviewed strings: `Format`, `Fargetema` (`grønn`, `blå`, `brun`, translated
  from Figma's `alt 1/2/3`), `Bakgrunn`, `Geometrisk form` and `Karakter`.
- Only these are exported: components and linked instances in the mapping. Loose `motif` groups,
  guide frames starting with `_`, the `Navngivingsstruktur` section and some off-page instances
  in Internbruk were reviewed and left out. `suggest:figma` skips the sections and nodes listed in
  `scripts/exclusions.json`; add an entry there (with a reason) to exclude more.
- SVGs are checked before use. Scripts, external URLs, entities and `foreignObject` are rejected.
  Embedded base64 PNG, JPEG and WebP images on `<image>` elements are allowed.

## Tags

The search also matches tags, by prefix ("kont" finds "kontor"). Tags are read from the component set's
description in Figma, as comma-separated words such as `kontor, retning, piler`. An optional `Tags:`
prefix is accepted. `sync:figma` stores them as `tags` in `metadata.json` and the preview dialog shows
them. They are not part of `import-map.json`, so editing a tag needs only a new sync and a commit.

## Adding or changing families

To add an illustration (or a whole family) that already exists in Figma:

1. In Figma, name the component set like the others and put its tags in the description.
2. Run `suggest:figma --category=<id>` and review the diff of `source/import-map.json`.
   If it reports an ambiguity, fix it in Figma or edit the map by hand.
3. Run `sync:figma --category=<id>`. It validates ancestry, references and bounds against Figma.
4. Optionally run `build:assets` to preview the artwork locally.
5. Commit `import-map.json` and `metadata.json`. The deploy workflow fetches and uploads the artwork.

For a new category, first add its entry to `sources` in `src/schema.ts`.

`suggest:figma` derives IDs, property labels and the `alt N` colour themes with the rules in
`scripts/planning.ts`.
